# 2) كيف نحوّلها تطبيق جوال — الخطة التقنية

## 2.1 القرار الأول: تطبيق واحد أم اثنان؟

**تطبيق واحد بدورين** (مالك / مزوّد يُختار عند التسجيل، ويمكن الجمع بينهما).

لماذا ليس تطبيقين مثل نمط "كابتن/عميل"؟
- كثير من المقاولين الصغار هم أنفسهم ملّاك يبنون.
- تطبيقان = ضعف تكلفة التطوير والنشر والصيانة، ونحن في مرحلة تحتاج سرعة.
- التبديل بين الدورين تبويب واحد داخل التطبيق.

## 2.2 حزمة التقنية المقترحة

| الطبقة | الاختيار | السبب |
|---|---|---|
| تطبيق الجوال | **Flutter** | كود واحد لـ iOS/Android، دعم RTL/العربية ممتاز، أداء جيد للقوائم والصور. (React Native بديل مقبول إذا كان الفريق من خلفية JS) |
| الخلفية | **Supabase** (Postgres + Auth + Storage + Realtime) | يغطي OTP والمحادثة الفورية وتخزين الصور وقواعد الوصول Row-Level Security بدون بناء خادم من الصفر — أسرع طريق لـ MVP |
| الإشعارات | Firebase Cloud Messaging | المعيار الفعلي للمنصتين |
| الخرائط والجغرافيا | خرائط Google / Mapbox + PostGIS للاستعلام "مزوّدون ضمن 15 كم" | فرز الحي هو ميزة جوهرية، فالجغرافيا تدخل قاعدة البيانات من اليوم الأول |
| رفع الصور | ضغط على الجهاز قبل الرفع + صور مصغّرة | صور مواقع البناء كبيرة وشبكات المواقع ضعيفة |
| التحقق | OTP عبر مزوّد رسائل محلي، والتحقق من السجل/العمل الحر يدويًا في البداية | لا تؤتمت التحقق قبل أن يكون لديك حجم يبرره |

> ملاحظة: عندما ينمو المنتج، يمكن استخراج خدمات (مطابقة العروض، الفوترة) من Supabase إلى خدمات مستقلة — لكن ليس قبل وجود مستخدمين حقيقيين.

## 2.3 نموذج البيانات (مبسّط)

```
users            (id, phone, name, role[owner|provider|both], city, created_at)
providers        (user_id, business_name, verified, cr_number?, freelance_doc?,
                  specialties[], service_center geog, service_radius_km,
                  response_avg_minutes, commitment_score)
projects         (id, owner_id, type[villa|building|renovation|finishing],
                  city, district, location geog, land_area, floors,
                  status, current_stage_no, created_at)
stages           (id, project_id, stage_no, name, state[locked|active|done],
                  opened_at, closed_at)
stage_photos     (id, stage_id, url, taken_at)
rfqs             (id, stage_id, description, budget_range?, state[open|closed],
                  max_offers=5, expires_at)          -- طلب العروض
offers           (id, rfq_id, provider_id, price?, duration_days?, note,
                  state[submitted|shortlisted|accepted|rejected])
conversations    (id, offer_id)                       -- تُفتح فقط بعد وجود عرض
messages         (id, conversation_id, sender_id, body, attachments[], created_at)
reviews          (id, stage_id, provider_id, punctuality, quality,
                  price_match, cleanliness, comment, created_at)
badges           (id, provider_id, type, earned_at, criteria_snapshot jsonb)
price_index      (id, city, material, unit, price, week)
stage_templates  (project_type, stage_no, name, provider_categories[])
```

نقاط تصميمية مهمة:
- **المحادثة لا تُنشأ إلا عن عرض** — هذا يمنع السبام هيكليًا لا بالمراقبة.
- الشارات تُحسب بمهمة مجدولة أسبوعية من الجداول الأخرى، مع حفظ لقطة المعايير وقت المنح.
- `stage_templates` يجعل إضافة مسار جديد (ترميم، تشطيب فقط) تعديل بيانات لا تعديل كود.

## 2.4 قواعد المطابقة (خوارزمية الإصدار الأول — بسيطة عمدًا)

عند فتح طلب عروض:
1. رشّح المزوّدين: تخصص المرحلة ∩ نطاقهم الجغرافي يغطي موقع المشروع ∩ موثّقون.
2. رتّبهم: مسافة أقرب ← تقييم أعلى ← استجابة أسرع.
3. أرسل الإشعار على دفعات (أقرب 10 أولًا، ثم وسّع كل 6 ساعات إن لم يكتمل السقف).
4. أغلق عند 5 عروض أو 48 ساعة، أيهما أسبق.

لا تعلّم آلة ولا تعقيد — هذه القواعد تكفي لأول 10,000 مشروع.

## 2.5 الأمان والخصوصية والأنظمة

- رقم جوال المالك و**الموقع الدقيق** للمشروع لا يظهران إلا بعد قبول عرض؛ قبلها يظهر الحي فقط. (موقع بيت قيد الإنشاء معلومة حساسة أمنيًا).
- Row-Level Security على كل الجداول: المالك يرى مشاريعه، والمزوّد يرى الطلبات المرشّح لها فقط.
- التوافق مع نظام حماية البيانات الشخصية السعودي (PDPL): تخزين داخل المملكة أو مزوّد متوافق، وسياسة خصوصية واضحة.
- طالما لا تمرّ الأموال عبر المنصة، فالمتطلبات التنظيمية خفيفة — وهذا سبب إضافي لتأجيل المدفوعات.
- الإبلاغ عن مزوّد + حظر + مراجعة يدوية للبلاغات في البداية.

## 2.6 خطة التنفيذ

| المرحلة | المدة التقديرية | التسليم |
|---|---|---|
| 0. النموذج الأولي | 2–3 أسابيع | تصميم Figma للرحلتين + اختباره على 5 ملّاك و5 مقاولين حقيقيين **قبل كتابة أي كود** |
| 1. الهيكل | 4 أسابيع | تسجيل OTP، إنشاء مشروع، خط المراحل، ملفات المزوّدين (إدخال يدوي للمزوّدين الأوائل) |
| 2. السوق | 4 أسابيع | طلب العروض، العروض، المحادثة، الإشعارات |
| 3. الثقة | 3 أسابيع | التقييمات، الشارات، التحقق، حاسبة الكميات ومؤشر الأسعار |
| 4. إطلاق تجريبي | 4–6 أسابيع | حي واحد في مدينة واحدة (التفصيل في `03-gtm.md`) |

المجموع الواقعي: **4–5 أشهر** لفريق صغير (مطوّر Flutter + مطوّر خلفية/مشترك + مصمم جزئي) حتى الإطلاق التجريبي.

## 2.7 ما الذي يقيس النجاح تقنيًا

- زمن فتح التطبيق حتى أول شاشة مفيدة < 2 ثانية على شبكة متوسطة.
- نسبة نجاح رفع الصور من مواقع البناء (شبكة ضعيفة) > 95% مع إعادة المحاولة التلقائية.
- وصول الإشعار للمزوّد خلال دقيقة من فتح طلب العروض.
